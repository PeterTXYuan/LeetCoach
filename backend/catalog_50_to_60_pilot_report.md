## Generator and usage

- Actual local `codex exec` model: `gpt-5.6-sol`, Medium reasoning, ChatGPT CLI authentication. Groq was not used.
- Ten calls produced ten structured drafts and passed the existing importer-shape validation on the first attempt. **First-pass schema success: 10/10; editorial acceptable without changes: 6/10.** Four raw editorial drafts needed teaching/approach corrections; four records needed related-category edits originating in the factual input. Counting both types of edit, only 3/10 raw records could have been staged unchanged. The untouched raw drafts remain in `catalog/drafts/pilot_60/` for comparison.
- Retries/regenerations: **0**. Failed attempts: **0**. Each `.checkpoints/<slug>.json` has one generation attempt and its measured usage.
- Total recorded generator usage: **148,382 input tokens**, **5,069 output tokens**; of those, 51,072 input tokens were reported cached and 453 output tokens reasoning. Mean per problem: **14,838 input / 507 output tokens** (15,345 combined). The CLI process ran approximately **136 seconds** from 06:17:26 UTC to the final checkpoint at 06:19:42 UTC.
- Resume check: a second generator invocation skipped **10/10**, made **zero** new model calls, and preserved the same cumulative usage. The latest `catalog/drafts/pilot_60/report.md` shows the resume result; the individual checkpoint files preserve generation attempts.
- Factual-input preparation and independent review consumed Codex work in this conversation, but those tokens are not instrumented by the CLI generator. They are **not included** in the usage totals above and cannot be quantified reliably from repository records.

## Disposable database and API test

The one-off test `catalog/drafts/pilot_60/verify_import.py` used a **fresh migrated temporary SQLite database**. It seeded the 40 stable problems, imported the ten previously approved JSON records, snapshotted **all 50 rows and owned child IDs/content**, then imported test-only copies of the ten staged records with a temporary approval flag. This test-only copy was explicitly authorized; it was deleted after import, and the actual staged files remain `provenance.reviewed: false`. `load_catalog` rejected the real staged directory as required.

Results: **60 distinct real problems**, **240 submission templates**, exactly one primary approach for each new problem, four-language context retrieval for all ten, no foreign-key errors, and **zero changes** to the original 50 snapshot. A repeat import marked all ten unchanged and preserved the entire 60-row snapshot. Analysis, Related, and Hints returned HTTP 200 for all ten. A mocked provider exercised the Policy 9 guidance route for all ten primary approaches, each returning `policyVersion: 9`; no Groq request was made. The disposable test passed **1/1**. This is interface integration, not generated-code correctness testing.

Existing backend suite: `py -B -m unittest discover -s tests` — **153 tests passed in 135.844 seconds**. The suite's apparent "live" evaluation lines are mocked harness tests; this pilot made no Groq calls. Disposable pilot check: `py -B catalog/drafts/pilot_60/verify_import.py` — **1 test passed** (rerun after editorial edits).

## Workflow assessment and review files

The generator removed repetitive prose drafting: all ten descriptions, approaches, complexity explanations, thinking steps, and signal lists arrived as structurally valid drafts in a little over two minutes. It did **not** remove manual fact sourcing, four-language contract checks, related-card choices, or algorithm review. The two potentially impractical secondary approaches and several classification/signal issues show why the review gate remains necessary. CLI input-token overhead is substantial relative to the short factual prompt.
